# AutoCare

Connected automotive service platform pairing vehicle owners, renters, service centers, parts vendors, delivery agents, and fleet operators.

## Run & Operate

- `pnpm --filter @workspace/api-server run dev` — API server (port 5000)
- `pnpm --filter @workspace/autocare run dev` — web app
- `pnpm run typecheck` — full typecheck
- `pnpm run build` — typecheck + build
- `pnpm run test` — run all workspace test suites
- `pnpm --filter @workspace/api-spec run codegen` — regen hooks + Zod schemas from OpenAPI
- `pnpm --filter @workspace/db run push` — push DB schema (dev only)
- Required env: `DATABASE_URL`
- Split-domain deploys (e.g. Render: static web site + separate API service): set web build-time env `VITE_API_BASE_URL` to the API server's absolute origin (e.g. `https://autocare-api.onrender.com`, no trailing `/api`). Unset → same-origin `/api` proxy (Replit default). See `artifacts/autocare/src/lib/api-base.ts`. Note: two-origin deploys also need server CORS (`Access-Control-Allow-Credentials` + specific origin) and `SameSite=None; Secure` session cookies — not yet wired.

## Stack

- pnpm workspaces, Node.js 24, TypeScript 5.9
- API: Express 5 + Zod, contract-first OpenAPI
- DB: PostgreSQL + Drizzle ORM
- Web: React 19 + Vite, wouter, TanStack Query, shadcn/ui, Tailwind v4, framer-motion, recharts, sonner
- Codegen: Orval (React Query hooks + Zod schemas)
- Build: esbuild (CJS bundle)

- `lib/db/src/schema/subscriptionPlans.ts` — `PlanLimits` type + `DEFAULT_PLAN_LIMITS`; the jsonb `limits` column is the source of truth for enforced entitlements
- `lib/db/src/schema/drivers.ts` — chauffeur profiles (scoped by ownerPhone)
- `lib/db/src/schema/{tripLocations,rentalIncidents}.ts` — rental-booking-scoped GPS pings + safety reports
- `lib/db/src/schema/organizations.ts` — `organizations`, `organization_members`, `organization_preferred_centers`; `vehicles.organizationId` + `vehicles.assignedDriverPhone`
- `lib/db/src/schema/fleetTracking.ts` — vehicle-scoped fleet GPS + incidents (distinct from rental-booking-scoped tables)
- `lib/db/src/schema/fleetPartsOrders.ts` — org-scoped parts orders with approval workflow
- `lib/db/src/schema/paymentTransactions.ts` — provider-agnostic payment transaction ledger (currently PaySwitch only). Each row carries `purpose` + `purposeRef` (`subscription` | `service_invoice` | `parts_order_approve_and_pay` | `parts_order_center_pay` | `rental_booking`), `amount` in pesewas, `status` (pending/successful/failed), `successRedirect` / `failureRedirect` resolved at init time. Subscriptions add a new status value `pending_payment` (used between init and callback).
- `lib/db/src/schema/sellerPayouts.ts` — money owed to a seller after a successful charge. Unique on (`saleKind`,`saleId`). `sellerKind` ∈ owner/center/vendor; `sellerId` is `text` (phone for owner, uuid for center/vendor). Statuses: `needs_account` → `pending` → `paid`, with `failed` for disbursement errors. Tracks `attempts`, `lastError`, `reference` (PaySwitch txn or manual bank/MoMo ref), `manualNote`. The shared `PayoutAccount` jsonb type is mirrored on `service_centers.payoutAccount`, `vendors.payoutAccount`, and `users.payoutAccount` (rental owners use their user row keyed by phone).
- `lib/db/src/seed.ts` — demo data

### Server
- `artifacts/api-server/src/routes/` — Express handlers per resource
- `artifacts/api-server/src/lib/entitlements.ts` — `getEntitlements(kind,id)`, `getOwnerEntitlementsForVehicle`, `featuredSubscriberIds`; every plan-gated action goes through here
- `artifacts/api-server/src/lib/payswitch.ts` + `routes/payswitch.ts` — PaySwitch (TheTeller) integration. `initiateCheckout()` POSTs to `test.theteller.net/checkout/initiate` (or live) with HMAC Basic auth, 12-digit `transaction_id`, amount in pesewas (cedis × 100, zero-padded 12 digits). Init routes (all auth, all create a `payment_transactions` row in `pending` + return `checkoutUrl`): `POST /payments/payswitch/subscriptions`, `POST /payments/payswitch/service-invoices/:invoiceId`, `POST /payments/payswitch/parts-orders/:orderId/approve-and-pay`, `POST /payments/payswitch/parts-orders/:orderId/center-pay`, `POST /payments/payswitch/parts-orders/:orderId/direct-buy`, `POST /payments/payswitch/rental-bookings/:bookingId`. Direct-buy parts orders are created server-side in status `awaiting_payment` (stock reserved up-front; cancelling refunds it); the buyer redirects to PaySwitch from Checkout (single-seller cart) or from each OrderDetail "Complete payment" panel (multi-seller cart). `GET /me/subscriber-options` still lists the audiences the caller may subscribe for. `GET /payments/payswitch/callback?txn=…&code=…&status=…` (NO auth, mounted BEFORE `requireKycVerified`) — query-string status is **never trusted**, the handler ALWAYS calls `checkTransactionStatus(txn)` server-to-server against `/v1.1/users/transactions/:txn/status` and only settles when the provider reports `code:"000"` + status `approved`/`successful`. Amount mismatch between the verified response and our `payment_transactions.amount` also fails settlement. Three independent settlement entry points all funnel through one shared `settleVerifiedTransaction(txn, verified, log)` dispatcher (exported from `routes/payswitch.ts`): the browser callback above, `POST /payments/payswitch/webhook` (PaySwitch's status-notification webhook — public, body untrusted, ignores everything except the `transaction_id` and re-verifies server-to-server, always replies 200), and `reconcilePendingPayments()` (in `lib/paymentReconciler.ts`) which sweeps `payment_transactions` rows stuck in `pending` past `PAYMENT_RECONCILE_STALE_AFTER_MS` (default 10 min) and re-checks each one with PaySwitch. The reconciler ticks every `PAYMENT_RECONCILE_INTERVAL_MS` (default 5 min) from the in-process scheduler in `index.ts`; opt out with `DISABLE_PAYMENT_RECONCILER=1`. Idempotency comes from a `WHERE status='pending'` CAS on the txn flip plus domain handlers that short-circuit when the sale is already in its post-payment state, so concurrent callback + webhook + reconciler runs all converge safely. The dispatcher then dispatches by the txn row's `purpose`: subscription flip; `closeInvoiceAsPaid` for service invoices; `approveProposalAndReserveStock` (or stamp `paid_by_owner/paid_by_center`) for mechanic-proposed parts orders; direct-buy parts orders flip from `awaiting_payment` to `delivered` (center-shop, on-hand) or `placed` (vendor) with `paid_by_owner`; rental bookings flip from `awaiting_payment` to `confirmed`+`paid`. The legacy mock-payment endpoints (`POST /invoices/:id/pay`, `POST /orders/:id/approve-and-pay`, `POST /orders/:id/center-pay`, and `PATCH /rental-bookings/:id { payment: { method: "online", markPaid: true } }`) are now **admin/super_admin-only** — preserved as back-office manual-settlement tools but no longer reachable by public buyers, who must go through the PaySwitch init + callback path. On every successful sale callback (excluding subscriptions) it also calls `recordCommission*` to log platform revenue **and** `createPayoutForSale` (lib/payouts.ts) which records a `seller_payouts` row and immediately attempts `disburseToSeller` if `PAYSWITCH_DISBURSE_API_USER`/`KEY` are configured. Redirects always land on `/billing/result?status=…&purpose=<kind>&…ids…` with reason on failure. Env: `PAYSWITCH_MERCHANT_ID`, `PAYSWITCH_API_USER`, `PAYSWITCH_API_KEY` required for charging; `PAYSWITCH_DISBURSE_API_USER` / `PAYSWITCH_DISBURSE_API_KEY` optional for Direct Pay (when missing, payouts queue as `pending` for manual settlement); `PAYSWITCH_ENV=test|live` (default test); `PUBLIC_BASE_URL` overrides the redirect origin.
- `artifacts/api-server/src/lib/payoutAlerts.ts` — stuck-payout sweep. `runPayoutStuckAlerts()` finds every `seller_payouts` row in `needs_account` / `pending` / `failed` older than `PAYOUT_STUCK_THRESHOLD_MS` (default 24h), drops a `kind:"payout_stuck"` in-app notification (deduped per `payout_stuck:<payoutId>:<UTCdayBucket>`) into every active admin + super_admin queue, and emails a single digest of *newly* alerted rows to `PAYOUT_ALERT_EMAILS` (or every active super_admin email when unset) via `payoutStuckDigestEmail` in `lib/email.ts`. Scheduler in `index.ts` ticks every `PAYOUT_STUCK_INTERVAL_MS` (default 6h, opt out with `DISABLE_PAYOUT_STUCK_SCHEDULER=1`).
- `artifacts/api-server/src/lib/paymentStuckAlerts.ts` — stuck-payment alarm, called at the end of every `reconcilePendingPayments()` tick. `maybeAlertStuckPayments({staleAfterMs, unreachable})` trips when either the count of `payment_transactions` rows stuck in `pending` past the stale cutoff reaches `PAYMENT_STUCK_ALERT_THRESHOLD` (default 10) **or** the number of unreachable PaySwitch verifications in the sweep reaches `PAYMENT_STUCK_UNREACHABLE_STREAK` (default 5 — the PaySwitch-outage signal). On trip it drops a `kind:"payment_stuck"` in-app notification (deduped per `payment_stuck:<UTCdayBucket>`) into every active **super_admin** queue (note: super_admins only, unlike payout alerts) and emails `paymentStuckAlertEmail` to the same recipients as reminder failures (`REMINDER_ALERT_EMAILS`, else all active super_admins). Email fires only on the first alerting sweep of the UTC day (gated on a freshly-created notification). Never throws; failures are caught in the reconciler so they can't break settlement.
- `artifacts/api-server/src/lib/payouts.ts` + `routes/payouts.ts` — seller-payout engine. `createPayoutForSale({saleKind, saleId, sellerKind, sellerId, grossAmount, commissionAmount})` writes a `seller_payouts` row (unique on `saleKind`+`saleId`; `netAmount = gross − commission`) and either disburses via PaySwitch `/v1.1/transaction/process` (Direct Pay / MoMo) or leaves it `pending`/`needs_account` for the super-admin queue. `disburseToSeller` resolves the destination via `resolve{Owner,Center,Vendor}Seller` (reads the `payout_account` jsonb column from `users` / `service_centers` / `vendors`). Routes: `PUT|GET /me/payout-account` (owner — uses session phone), `PUT|GET /service-centers/:id/payout-account` (gated by `authorizeCenterStaff`), `PUT|GET /vendors/:id/payout-account` (gated by `authorizeVendorStaff`), plus admin queue `GET /admin/payouts?status=…`, `POST /admin/payouts/:id/retry`, `POST /admin/payouts/:id/mark-paid` (records bank/MoMo reference for off-PaySwitch settlements). Saving a payout account triggers `retryPayoutsForSeller` so any waiting rows flush immediately.
- `artifacts/api-server/src/routes/onboarding.ts` — KYC submit, super-admin approval queues, `requireKycVerified` middleware
- `artifacts/api-server/src/lib/reminders.ts` — `runReminderJob(trigger)` wraps the generator and records to `reminder_runs`; in-process scheduler in `index.ts` calls it on a recurring interval (default 24h, `REMINDER_INTERVAL_MS` / `DISABLE_REMINDER_SCHEDULER=1` to override). Every successful run also calls `pruneOldReminderRuns()` to delete `reminder_runs` rows older than `REMINDER_RETENTION_DAYS` (default 90) so the audit table stays bounded. On `status=error` the run drops an in-app `reminder_job_failed` notification into every active admin/super_admin's queue (deduped per error+UTC day via dedupe key `reminder_failure:<dayBucket>:<sha1prefix>`), and emails the configured recipients once the consecutive-failure streak reaches `REMINDER_FAILURE_ALERT_THRESHOLD` (default 3). Email recipients come from `REMINDER_ALERT_EMAILS` if set, else every active super_admin's email.
- `scripts/src/runReminders.ts` — standalone entry point (`pnpm --filter @workspace/scripts run reminders:run`) for Replit Scheduled Deployments; records each run as `trigger=external`
- `artifacts/api-server/src/routes/organizations.ts` — fleet endpoints (intentionally outside OpenAPI; plain Express + Zod)

## Architecture decisions

### Foundations
- **Contract-first**: every API change goes OpenAPI → codegen → server route + client hook. Server handlers consume the generated Zod schemas, so types cannot drift. Exceptions (intentionally outside OpenAPI, single-client + plain Express+Zod): the maintenance-history CSV/PDF routes and all fleet endpoints.
- **Role switch is localStorage-backed**, driving navigation and which actions appear on shared pages. Renter and fleet are first-class roles with their own dashboards and trimmed sidebars (`RENTER_NAV`, `fleetNavFor()`).
- **Booking lifecycle** is a finite-state machine guarded server-side (`requested → accepted → in_progress → awaiting_approval → approved → completed`, with `cancelled`/`rejected` terminals); UI only surfaces legal transitions.
- **Conditional query hooks** require both `enabled` and an explicit `queryKey` — always pair `{ enabled, queryKey: getXQueryKey(id) }`. Invalidate via the same helper.

### Rentals
- A car carries `rentalModes: ('self_drive' | 'with_driver')[]`. `with_driver` requires a `driverId` owned by the same `ownerPhone`; dropping `with_driver` nulls `driverId`. With-driver bookings use `withDriverDailyRate` (falls back to `dailyRate`).
- Renter KYC minimum is a government ID photo; licence is optional. Use `isProfileReadyForBooking` for the base gate and `isProfileReadyForMode(profile, mode)` to require licence for self-drive.
- KYC approval is admin-only: `PATCH /renter-profiles/:id` returns **403** when a non-admin sends `kycStatus`. `UpsertRenterProfileInput` doesn't expose the field at all.
- `authorizeBookingAccess` in `routes/rentals.ts` is the single auth helper for any single-booking tracking/incident/signature endpoint — admin OR booking renter (by `req.user.phone`) OR car owner (by `ownerPhone`). Do not add new IDOR-prone routes without it.
- Incidents derive `reportedBy` from the verified relationship, not the request body. Renter-submitted GPS becomes a `trip_locations` ping + `lastKnown*`.
- **Owner/chauffeur PII redaction**: `GET /rental-cars` and `GET /rental-cars/:id` strip `ownerPhone`/`ownerEmail`/driver contact unless caller is admin, the car's owner, or a renter with a booking on the car in `contract_pending|awaiting_payment|confirmed|active|completed` (constants `OWNER_PII_BOOKING_STATUSES` / `DRIVER_PII_BOOKING_STATUSES` in `routes/rentals.ts`). Per-row owner self-unredact preserves "My Listings".
- **Share-link CTA** (`pages/rentals/SharedCar.tsx`) branches on auth: anonymous → Create renter account + Sign in (both `?next=/rentals/<id>`); signed-in non-renter → disabled "Switch to renter"; renter no-KYC → finish KYC; renter ready → book.

### Service bookings & parts orders
- `routes/bookings.ts` + `routes/invoices.ts` enforce ownership via `authorizeServiceBooking(req, res, bookingId)` — admin, vehicle owner (by phone), or center staff (`center_staff` table). Owner-only actions: approve/pay invoice. Center-only: status transitions, assign mechanic, create invoice. List endpoints are scoped per caller.
- `POST /orders` derives buyer identity from `req.user` (direct buy) or the booking's vehicle owner (proposal), never from the body — buyer name/phone can't be spoofed. `GET /orders?mine=true` scopes by session phone; only admin/vendor see the unfiltered list. Direct-buy checkout prefills shipping from the buyer's most recent direct-buy order (filter is `!bookingId && !mechanicId`, not status-based, so proposal orders never leak the service-center address).
- **Two seller kinds — vendor vs service-center shop**: a Part may be sold by a third-party vendor (`parts.vendorId`) OR by a service center from its own on-hand shelves (`parts.centerId`). Exactly one is set. `POST /orders` derives the seller from the line items (it rejects mixed-seller / multi-seller carts) and cross-checks against `vendorId` / `sellerCenterId` in the body. Center-sourced orders are stamped `fulfillmentKind="on_hand"` and the server auto-fills `confirmedAt` / `shippedAt` / `deliveredAt` + `shippingFee=0` at create time (proposals get the same auto-deliver treatment in `approveProposalAndReserveStock`). No delivery agent ever attaches. Centers manage their on-hand catalog at **`/center/shop`** (Web → "My Shop") via the plain-Zod `GET|POST /service-centers/:centerId/parts` routes (intentionally outside OpenAPI; gated by `authorizeCenterStaff`). Cart, Checkout, OrderDetail and PartCard branch on `sellerKind`: center-sourced groups hide vendor / ship-to / delivery-agent panels and show a "Service-center shop · on hand · no delivery" card instead.
- **Parts payment routing** (mechanic proposals only): owner picks one of two payment paths at approval time via dedicated endpoints — `POST /orders/:orderId/approve-and-pay` (owner pays seller directly; sets `paymentStatus=paid_by_owner`, reserves stock, status → `placed`) or `POST /orders/:orderId/authorize-center-pay` (owner authorizes the service center to settle with the vendor; sets `centerPayAuthorized=true`, reserves stock, status → `placed`, `paymentStatus` stays `unpaid`). For **center-sourced** proposals the center IS the seller, so `authorize-center-pay` stamps `paymentStatus=paid_by_center` directly (no two-step settlement) and the parts roll onto the service invoice the normal way. The legacy `PATCH /orders/:orderId/status` no longer accepts `proposed → placed` — rejection (`proposed → cancelled`) still flows through it. Center staff settle vendor-sourced authorized orders via `POST /orders/:orderId/center-pay`. At service-invoice creation time (`POST /bookings/:bookingId/invoice`) the server auto-appends every `paid_by_center` order's line items to the invoice as `kind:"part"` entries (description `"Part: <name> (paid by service center)"`) and stamps `invoicedAt` on those orders so the same parts can never be billed twice. Direct-buy orders are stamped `paid_by_owner` at creation. UI surfaces a `PaymentBadge` (`unpaid` / `paid_by_owner` / `paid_by_center`, with an "Awaiting center payment" variant when authorized but still unpaid) on `OrderDetail` and on the parts-orders panel of `BookingDetail`.
- **Fleet-aware proposal approval**: when a proposal targets an org-attached vehicle (`vehicle.organizationId` set), the "owner" approval gate in `authorizeProposalAction` accepts any **admin or finance** member of the org — and any other member whose `canCheckoutDirectly` override is on — via `callerActsAsOrgOwner()`. The same approve-and-pay / authorize-center-pay endpoints work unchanged; the org just stands in for the individual vehicle owner.

### Subscriptions & entitlements
- Plans carry `features` (marketing copy on the plan card) and `limits` (`PlanLimits`, machine-enforced). Server gates only ever read `limits`. `getEntitlements` orders by `subscriptions.startedAt DESC` so multiple active subs resolve to the newest plan deterministically. Free-tier defaults live in `FREE_LIMITS` inside `entitlements.ts`.
- Quotas enforced today:
  - center `maxBookingsPerMonth` → `POST /bookings` (402 quota_exceeded)
  - vendor `maxPartsListed` → `POST /vendors/:vendorId/parts`
  - owner `priorityBooking` materialised on `bookings.priority` at create (ORed with org Fleet Pro when vehicle is org-attached)
  - owner `canExportHistory` → maintenance-history CSV/PDF
  - org `maxFleetVehicles` → `POST /organizations/:orgId/vehicles`
  - org `partsCostTransparency` → `GET /organizations/:orgId/parts-spend`
  - org `canExportHistory` → both fleet maintenance-history routes
- `featuredPlacement` floats centers/vendors to top of their directories. `dedicatedSupport` is a UI/marketing flag (no server gate).

### Fleet (organizations)
- `subscriberKind = "organization"`. Orgs have a many-to-many **preferred-pool** of service centers; `POST /bookings` enforces the pool when `vehicle.organizationId` is set (platform admins can override).
- `requireOrgMember(req, res, orgId, minRole?)` is the single fleet auth helper — platform admins synthesize an `admin` membership.
- Org member roles (`ORG_MEMBER_ROLES`): **admin** (full), **finance** (parts-order approval + billing), **manager** (places orders, day-to-day), **driver** (assigned vehicles + parts requests).
- **Parts-order approval** is org-scoped: when `organizations.requireFinanceApproval` is on, manager/driver checkouts create a `fleet_parts_orders` row in `pending_finance`. `organization_members.canCheckoutDirectly` overrides per-member. Admins + finance always bypass. Vendor-side fulfilment is intentionally NOT wired — "paid" represents approval + ledger settlement; the demo stops there.
- **Maintenance-history export** (CSV + PDF) at owner scope (`/vehicles/:vehicleId/maintenance-history.{csv,pdf}`) and fleet scope (`/organizations/:orgId/...` + per-vehicle, latter allows assigned driver). PDF streamed via `pdfkit` (external in `build.mjs` along with `fontkit`+`brotli` due to CJS resolution under esbuild). Hard cap 5000 rows. Two separate routes per format because Express 5 path-to-regexp rejects `:format(csv|pdf)`.

## Product

- **Owner**: dashboard with status breakdown + reminders, garage, center browser, multi-step booking, timeline, invoice approval + payment.
- **Service center**: control-panel dashboard, incoming-requests queue, active jobs, mechanic roster, accept/assign/invoice/complete workflow.

Also accesses the shared Parts Marketplace via `buyersOnly` (now allows `fleet`).

## Onboarding & approvals

- **Self-signup at `/signup`**: anyone applies as owner / renter / center / vendor / delivery / fleet. Form is role picker → role-specific details → `POST /auth/signup` with `requestedRole` + `applicantData`. Applicants get `approvalStatus=pending` + `kycStatus=not_submitted` and **no** session cookie until a super admin approves.
- **Legacy `/auth/signup`** (no `requestedRole`, used by the rentals quick-signup) still auto-approves as `owner` and issues a cookie, so existing demo flows keep working. Seeded demo accounts are backfilled to `approved`+`verified` by `seedUsers.ts`.
- **Super-admin queues** at `/super-admin/approvals` (tabs: Applications / KYC / Rejected). Approve provisions the matching directory row (center / vendor / delivery / org with applicant as `admin` / renter-profile shell) keyed by phone; reject stores `approvalNote` shown on next login attempt.
- **Approved users land on `/onboarding/kyc`** with a role-specific checklist (gov ID + selfie for everyone; licence for renters & delivery; business reg for centers/vendors; org reg + sample vehicle reg for fleet). Uploads go through `@workspace/object-storage-web` `useUpload` and store as `/api/storage{objectPath}`. Resubmit flips `kycStatus` back to `submitted`.
- **Server enforcement**: `requireKycVerified` is mounted in `routes/index.ts` AFTER auth/storage/onboarding/landing-content but BEFORE every other resource router. Anonymous + admin/super_admin bypass; everyone else gets 403 `{reason}` until verified. `POST /auth/login` returns 403 `{reason:"pending"|"rejected", note?}` for non-approved users; `Login.tsx` shows banner UX.
- **Decision emails**: `PATCH /admin/approvals/:userId` + `PATCH /admin/kyc/:userId` fire a transactional email (approved / rejected / KYC verified / KYC rejected) via `lib/email.ts`. Fire-and-forget; failure never blocks the decision. Set `SENDGRID_API_KEY` (+ optional `EMAIL_FROM`) to enable delivery; without it the message is logged and `sendEmail` returns `{ok:false, reason:"not_configured"}`.
- **Per-document KYC rejection**: `PATCH /admin/kyc/:userId` accepts `documentDecisions: [{ key, reason }]` alongside the overall `decision`. When the reviewer marks specific docs, the server stamps `rejectionReason` + `rejectedAt` onto the matching `KycDocument` entries (other docs are left clean). `POST /me/kyc` rebuilds the docs array from scratch on the next submission, which naturally drops the rejection markers. The applicant-facing `/onboarding/kyc` page reads `user.kycDocuments[].rejectionReason` to highlight (red border + reason) only the docs that need re-upload. Per-doc reason inputs live in the Approvals reject dialog when `kind === "kyc"`.
- **Super-admin user management**: `GET /admin/owners` lists vehicle owners with their account status + vehicle count (joined by `ownerPhone`); UI at `/admin/owners` supports search, suspend (with reason — sets `approvalStatus=rejected`+ `approvalNote`), and reinstate. `PATCH /admin/users/:userId/status` powers the suspend/reinstate toggle (refuses to touch super_admin or yourself, records an `approvalEvents` row). `POST /admin/users` lets a super admin onboard any role manually at `/super-admin/onboard` — creates the user as `approved`+`verified` with both contact channels marked confirmed, reuses `provisionRoleRecord` to spin up the matching directory row (renter profile / service center / vendor / delivery agent / organization w/ applicant as `admin`), and returns a one-time `tempPassword` in the response (intentionally not emailed because the applicant didn't go through email verification).
- **KYC upload hardening** (`POST /me/kyc`): every submitted URL runs through `validateKycDocumentUrl` which (1) rejects anything not `/api/storage/objects/...` or `/objects/...`, (2) confirms the object exists in our private bucket via `getObjectEntityFile()`, (3) re-enforces `contentType ∈ {jpeg,png,webp}` and `size ≤ 10 MB` from GCS metadata (constants exported from `routes/storage.ts` as `ALLOWED_UPLOAD_MIME` / `MAX_UPLOAD_BYTES`). Validated docs are passed to `scanKycDocument` (`lib/kycScanner.ts`): ClamAV via `CLAMAV_HOST`+`CLAMAV_PORT`/`CLAMAV_SOCKET` when set (fail-closed; 503 if unreachable), with a local EICAR + magic-byte / MIME-mismatch heuristic always running first because clamd doesn't catch rename attacks. Infected uploads are moved to `quarantine/` via `objectStorageService.quarantineObjectEntity` and never referenced from the user row. Docs carry `scanStatus` / `scanCheckedAt` / `scanDetails`; the super-admin Approvals UI hides anything with `scanStatus !== 'clean'`. Scanner backend is pluggable (swap `getClam`/`scanStream` for VirusTotal/Cloudmersive without touching the route).

## Gotchas

- After editing `lib/db/src/schema.ts`, run `pnpm run typecheck:libs` once so other packages pick up new declarations.
- After editing `lib/api-spec/openapi.yaml`, run `pnpm --filter @workspace/api-spec run codegen` before touching server routes or web hooks.
- Adding a new `PlanLimits` field requires four edits: (1) the TS type + `DEFAULT_PLAN_LIMITS` in `lib/db/src/schema/subscriptionPlans.ts`, (2) `PlanLimits` in `lib/api-spec/openapi.yaml` + codegen, (3) every plan-seed `limits` in `scripts/src/seedPlatform.ts`, (4) `EMPTY_LIMITS` + `LIMIT_LABEL` in `pages/admin/Plans.tsx`. Missing any breaks typecheck via the generated Zod schema.
- Do not hand-edit files under `lib/api-client-react/src/generated/` — they're overwritten.
- Conditional query hooks must include both `enabled` and `queryKey`, otherwise TS rejects them.
